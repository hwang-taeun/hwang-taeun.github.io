홈서버 구축 — Synology NAS · Cloudflare · Let's Encrypt

집에 있는 Synology NAS와 Linux 서버를 개인 도메인으로 외부에서 안전하게 접속할 수 있게 만들었습니다. 도메인 등록과 DNS는 Cloudflare, 인증서는 Let's Encrypt를 쓰고, 유동 IP 반영과 인증서 갱신을 모두 API와 스크립트로 자동화했습니다.

도메인은 예시 myhomelab.example, 공인 IP는 문서용 대역(203.0.113.x, 198.51.100.x)으로 바꿨습니다. 화면은 모두 예시입니다.

1. 구성

도메인·DNSCloudflare Registrar + Cloudflare DNS (myhomelab.example)
공유기TP-Link AX3000, 외부 443 → NAS 5001 포트포워딩
NASSynology DSM (192.168.0.20) — 웹 관리, acme.sh, 작업 스케줄러, 국가 기반 방화벽
Linux 서버Rocky / Alma (192.168.0.21) — DDNS 스크립트(cron 5분)
인증서Let's Encrypt, myhomelab.example + *.myhomelab.example (ECC)

2. Cloudflare에서 도메인 등록

Cloudflare Registrar는 도메인을 원가에 팔고, 등록하면 같은 계정에 DNS 영역(Zone)이 자동으로 만들어집니다. 다른 등록 업체에서 산 뒤 네임서버만 Cloudflare로 바꾸는 방법도 있지만, 한 곳에서 관리하면 갱신·DNS·API를 같이 다룰 수 있어 편합니다.

  1. Cloudflare 계정 생성 → 계정 이메일 인증, 2단계 인증(2FA) 설정 (도메인을 잃지 않으려면 필수)
  2. 대시보드 Domain Registration → Register Domains에서 원하는 이름 검색
  3. 등록 기간, 자동 갱신 선택 → 등록자 연락처 입력 → 결제
  4. 등록 직후 등록자 이메일로 오는 연락처 확인 메일을 인증 (안 하면 도메인이 일시 정지될 수 있음)
  5. WHOIS 공개 정보는 기본으로 가려짐(Redaction) — 등록자 연락처는 Manage Domain → Contacts에서 확인·수정
Cloudflare Registrar는 모든 확장자를 지원하지 않습니다(예: 국가 도메인 일부). 원하는 확장자가 없으면 다른 업체에서 등록하고 네임서버를 Cloudflare 것으로 바꾸면, 아래 DNS·API 부분은 똑같이 쓸 수 있습니다.

3. DNS 레코드 설정 (대시보드)

DNS → Records → Add record에서 추가합니다.

프록시(주황 구름)를 끈 이유

  • 프록시를 켜면 도메인이 집 IP가 아니라 Cloudflare IP로 응답하고, 접속은 Cloudflare를 거쳐 들어옵니다. 집 IP를 숨기고 DDoS를 막아 주는 장점이 있습니다.
  • 하지만 Cloudflare 프록시는 정해진 포트만 중계합니다. DSM 기본 포트(5000·5001)는 그 목록에 없어서 DNS only(회색 구름)로 두었습니다.
  • 프록시를 켠 상태에서 "Always Use HTTPS"까지 켜면, 80 포트 요청이 NAS에 닿기 전에 Cloudflare에서 HTTPS로 넘겨져 인증서 HTTP 검증이 실패합니다. 인증서 문제를 볼 때 가장 먼저 확인할 부분입니다.

5. API로 레코드 조회·추가·변경·삭제

source /root/.cloudflare.env
CF="https://api.cloudflare.com/client/v4"
AUTH=(-H "Authorization: Bearer $CF_TOKEN" -H "Content-Type: application/json")

# 토큰 정상 여부
curl -s "${AUTH[@]}" "$CF/user/tokens/verify" | jq .result.status          # "active"

# Zone ID 조회
curl -s "${AUTH[@]}" "$CF/zones?name=myhomelab.example" | jq -r '.result[0].id'

# 레코드 목록 / 특정 레코드 찾기
curl -s "${AUTH[@]}" "$CF/zones/$ZONE_ID/dns_records" \
  | jq -r '.result[] | [.id,.type,.name,.content,.proxied] | @tsv'
RECORD_ID=$(curl -s "${AUTH[@]}" "$CF/zones/$ZONE_ID/dns_records?type=A&name=www.myhomelab.example" \
  | jq -r '.result[0].id')

# 추가 (POST)  — ttl 1 = 자동
curl -s -X POST "${AUTH[@]}" "$CF/zones/$ZONE_ID/dns_records" \
  -d '{"type":"CNAME","name":"*","content":"myhomelab.example","ttl":1,"proxied":false}'

# 일부만 변경 (PATCH) — 보낸 항목만 바뀜
curl -s -X PATCH "${AUTH[@]}" "$CF/zones/$ZONE_ID/dns_records/$RECORD_ID" \
  -d '{"content":"203.0.113.50"}'

# 전체 교체 (PUT) — 빠진 항목은 기본값으로 돌아가므로 type·name·content 모두 보냄
curl -s -X PUT "${AUTH[@]}" "$CF/zones/$ZONE_ID/dns_records/$RECORD_ID" \
  -d '{"type":"A","name":"www.myhomelab.example","content":"203.0.113.50","ttl":1,"proxied":false}'

# 삭제 (DELETE)
curl -s -X DELETE "${AUTH[@]}" "$CF/zones/$ZONE_ID/dns_records/$RECORD_ID"

6. DDNS 자동화 — 공인 IP가 바뀌면 A 레코드 수정

가정용 회선은 공유기 재부팅이나 통신사 사정으로 공인 IP가 바뀝니다. Linux 서버에서 5분마다 현재 IP를 확인해, 레코드와 다르면 수정하고 레코드가 없으면 새로 추가합니다.

#!/bin/bash
# /root/bin/cloud_dns.sh — 공인 IP 가 바뀌면 Cloudflare A 레코드 갱신 (없으면 추가)
source /root/.cloudflare.env                 # CF_TOKEN, ZONE_ID
CF="https://api.cloudflare.com/client/v4"
RECORDS=("myhomelab.example" "www.myhomelab.example")
TTL=1                                        # 1 = 자동
PROXIED=false
AUTH=(-H "Authorization: Bearer $CF_TOKEN" -H "Content-Type: application/json")
log(){ echo "[$(date '+%F %T')] $*"; }

# 현재 공인 IP (형식이 IP 가 아니면 중단 → 잘못된 값으로 레코드를 덮어쓰지 않음)
CURRENT_IP=$(curl -s --max-time 10 https://api.ipify.org)
[[ $CURRENT_IP =~ ^[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+$ ]] || { log "공인 IP 확인 실패: $CURRENT_IP"; exit 1; }
log "현재 공인 IP: $CURRENT_IP"

for NAME in "${RECORDS[@]}"; do
  INFO=$(curl -s "${AUTH[@]}" "$CF/zones/$ZONE_ID/dns_records?type=A&name=$NAME")
  ID=$(jq -r '.result[0].id // empty' <<< "$INFO")
  OLD=$(jq -r '.result[0].content // empty' <<< "$INFO")
  BODY=$(jq -nc --arg n "$NAME" --arg ip "$CURRENT_IP" --argjson ttl $TTL --argjson p $PROXIED \
           '{type:"A", name:$n, content:$ip, ttl:$ttl, proxied:$p}')

  if [ -z "$ID" ]; then                        # 레코드 없음 → 추가
    R=$(curl -s -X POST "${AUTH[@]}" "$CF/zones/$ZONE_ID/dns_records" -d "$BODY"); ACT="추가"
  elif [ "$OLD" = "$CURRENT_IP" ]; then        # 같음 → 그대로
    log "$NAME  변경 없음 ($OLD)"; continue
  else                                         # 다름 → 교체
    R=$(curl -s -X PUT "${AUTH[@]}" "$CF/zones/$ZONE_ID/dns_records/$ID" -d "$BODY"); ACT="업데이트 $OLD →"
  fi

  if [ "$(jq -r .success <<< "$R")" = "true" ]; then
    log "$NAME  $ACT $CURRENT_IP"
  else
    log "$NAME  실패: $(jq -c .errors <<< "$R")"
  fi
done
chmod 700 /root/bin/cloud_dns.sh
dnf install -y jq

# crontab -e
*/5 * * * * /root/bin/cloud_dns.sh >> /var/log/cloud_dns.log 2>&1
처음 스크립트는 레코드가 있을 때 수정만 했고, jq가 없을 때를 위한 grep 대체 코드가 함께 있었습니다. 지금은 jq를 필수로 두고, 레코드가 없으면 추가(POST)까지 하도록 정리했습니다.

7. 인증서: HTTP-01이 실패한 이유

DSM 제어판의 Let's Encrypt 발급은 HTTP-01 검증을 씁니다. Let's Encrypt가 http://도메인/.well-known/acme-challenge/…를 직접 열어 보고 정해진 값이 나오는지 확인하는 방식입니다.

  • DSM이 80 포트로 들어온 모든 경로를 로그인 페이지로 302 리디렉션해서, HTTPS 자동 리디렉션을 끄고 방화벽을 꺼도 해결되지 않았습니다.
  • 통신사에서 80 포트를 막는 경우에도 HTTP-01은 쓸 수 없습니다.
  • 그래서 80 포트를 아예 쓰지 않는 DNS-01 검증으로 바꿨습니다. 도메인 DNS에 _acme-challenge TXT 레코드를 올려 소유를 증명하는 방식이라, Cloudflare API로 자동화할 수 있고 와일드카드 인증서(*.myhomelab.example)도 받을 수 있습니다.

8. Synology에 acme.sh 설치·발급 (DNS-01)

# DSM: 제어판 → 터미널 및 SNMP → SSH 서비스 활성화 → 관리자 계정으로 접속 후
sudo -i

# acme.sh 설치 (DSM 에는 crontab 이 없어 스크립트 파일만 받아 사용)
cd /usr/local/bin
wget https://raw.githubusercontent.com/acmesh-official/acme.sh/master/acme.sh
chmod 755 acme.sh
mkdir -p /root/.acme.sh
acme.sh --set-default-ca --server letsencrypt     # 기본 CA 를 Let's Encrypt 로

# Cloudflare 토큰 (4번에서 만든 DNS 편집 토큰)
export CF_Token="발급받은_API_토큰"
export CF_Zone_ID="Zone_ID"

# 첫 발급 — 도메인 + 와일드카드
acme.sh --issue --dns dns_cf -d myhomelab.example -d '*.myhomelab.example' --keylength ec-256
  • 첫 발급에 성공하면 acme.sh가 토큰을 /root/.acme.sh/account.conf에 저장해 둡니다. 그래서 갱신 스크립트에는 토큰을 다시 넣지 않아도 됩니다. 이 파일 권한도 600인지 확인합니다.
  • 인증서 파일은 /root/.acme.sh/myhomelab.example_ecc/에 생깁니다 (.cer, .key, ca.cer, fullchain.cer).

9. DSM 인증서 자동 적용 스크립트

DSM은 인증서를 /usr/syno/etc/certificate/_archive/<ID>/ 폴더에 두고, 기본 인증서로 지정된 폴더 ID를 _archive/DEFAULT 파일에 적어 둡니다. 이 파일을 읽어 그 폴더의 내용만 덮어쓰면 GUI에서 "가져오기"를 할 필요가 없습니다. 역방향 프록시를 쓰면 프록시용 사본 폴더도 같이 갱신합니다.

#!/bin/bash
# /root/renew_cert.sh — DSM 작업 스케줄러에서 root 로 주 1회 실행
DOMAIN="myhomelab.example"
ACME=/usr/local/bin/acme.sh
CERT_DIR="/root/.acme.sh/${DOMAIN}_ecc"
ARCHIVE=/usr/syno/etc/certificate/_archive
LOG=/var/log/cert_renew.log
log(){ echo "[$(date '+%F %T')] $*" >> "$LOG"; }

# 1) 갱신 시기일 때만 갱신 (만료 30일 전부터). 토큰은 account.conf 에 저장되어 있음
"$ACME" --renew -d "$DOMAIN" --ecc --home /root/.acme.sh
rc=$?
if [ $rc -eq 2 ]; then log "갱신 시기 아님 (acme.sh exit 2) - 적용 생략"; exit 0; fi
if [ $rc -ne 0 ]; then log "갱신 실패 (acme.sh exit $rc)"; exit 1; fi

copy_cert() {                       # $1 = 대상 폴더
  cp -f "$CERT_DIR/$DOMAIN.cer"   "$1/cert.pem"
  cp -f "$CERT_DIR/ca.cer"        "$1/chain.pem"
  cp -f "$CERT_DIR/fullchain.cer" "$1/fullchain.pem"
  cp -f "$CERT_DIR/$DOMAIN.key"   "$1/privkey.pem"
}

# 2) DSM 기본 인증서 폴더에 적용
DEFAULT_ID=$(cat "$ARCHIVE/DEFAULT")
copy_cert "$ARCHIVE/$DEFAULT_ID"

# 3) 역방향 프록시용 사본에도 적용 (없으면 건너뜀)
n=0
for d in /usr/syno/etc/certificate/ReverseProxy/*/; do
  [ -d "$d" ] || continue
  copy_cert "$d"; n=$((n+1))
done

# 4) 웹 서버 재로드
synosystemctl reload nginx
log "갱신 완료 → DSM 기본 인증서($DEFAULT_ID) 와 역방향 프록시 ${n}개에 적용, nginx 재로드"
chmod 700 /root/renew_cert.sh
/root/renew_cert.sh          # 첫 테스트 (발급 직후라면 "갱신 시기 아님" 이 정상)
/usr/local/bin/acme.sh --renew -d myhomelab.example --ecc --force   # 강제 갱신으로 적용까지 시험할 때만

작업 스케줄러 등록

  1. 제어판 → 작업 스케줄러 → 생성 → 예약된 작업 → 사용자 정의 스크립트
  2. 일반: 작업 이름 SSL_Renew, 사용자 root
  3. 스케줄: 매주 일요일 03:00
  4. 작업 설정: 사용자 정의 스크립트 /root/renew_cert.sh, (선택) 실행 결과 메일 받기
처음 스크립트에서 바꾼 점
  • 처음에는 매달 --issue --force로 무조건 새로 발급했습니다. 동작은 했지만 필요 없는 발급이 쌓이고 Let's Encrypt 발급 횟수 제한에 가까워질 수 있어서, --renew로 바꾸고 주 1회 확인하게 했습니다. 갱신 시기가 아니면 acme.sh가 exit 2를 돌려주므로 그때는 적용을 건너뜁니다.
  • Cloudflare 키를 스크립트에 평문으로 넣지 않습니다 (account.conf에 저장된 토큰 사용).
  • 최초 1회는 DSM 제어판 → 보안 → 인증서 → 설정에서 각 서비스가 이 기본 인증서를 쓰도록 연결되어 있는지 확인했습니다. 이후로는 GUI 작업이 없습니다.

10. 접근 제어 — 국가 기반 방화벽

공유기(TP-Link AX3000)의 포트포워딩에는 출발지 IP를 제한하는 기능이 없어서, NAS의 방화벽에서 막았습니다.

DSM 제어판 → 보안 → 방화벽 → 규칙 편집 (위에서부터 처음 맞는 규칙 적용)
  1. 허용 : 출발지 IP  192.168.0.0/24 (집 내부 LAN)     모든 포트
  2. 허용 : 위치        대한민국                          모든 포트
  3. 거부 : 모두                                         모든 포트
  • 외부 여러 나라에서 접속을 시험해 주는 사이트로 확인했을 때 해외 노드는 대부분 차단되었습니다.
  • 한 해외 노드만 접속이 되었는데, GeoIP 데이터베이스가 그 IP를 국내로 잘못 분류한 경우였습니다. 국가 기반 차단은 GeoIP 정확도에 의존하므로 강력한 비밀번호, 2단계 인증, 자동 차단(로그인 실패 시)을 함께 켭니다.
  • 집 안에서 도메인으로 접속이 안 되면 공유기가 NAT 루프백(자기 공인 IP로 되돌아오는 접속)을 지원하지 않는 경우입니다. 휴대폰 데이터망으로 시험하면 구분할 수 있습니다.
