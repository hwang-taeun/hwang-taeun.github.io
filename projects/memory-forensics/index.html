침해사고 대응

IIS 웹 서버 침해사고 메모리 덤프 분석

"로그가 비어 있다"는 작은 단서에서 시작해, 메모리 덤프 분석으로 백신이 놓친 악성코드와 지속성 장치를 찾아내고 대응한 사례입니다.

1. 분석 환경

대상 시스템Windows Server 2016, IIS + ASP
서비스 유형고객 파일 업로드 서비스
설치 백신악성코드 미탐지
도구용도선택 이유
ProcDump (Sysinternals)메모리 덤프 수집Microsoft 공식 도구, 단일 실행 파일, 운영 서비스 영향 최소
Linux (strings, grep, file)덤프 분석대용량 텍스트 필터링과 파일 형식 판별
VirusTotal악성 여부 교차 검증약 60개 백신 엔진 동시 검사
생성형 AI검색 키워드 도출방대한 덤프에서 우선 확인할 침해 지표 선정

2. 최초 발견

  • 이벤트 뷰어 점검 중 특정 시간대 보안 로그가 반복적으로 비어 있는 구간을 발견했습니다.
  • 감사 정책을 확인하자 2~3분 주기로 '기록 안 함'으로 자동 변경되고 있었습니다.
  • 정상 시스템에서 감사 정책이 주기적으로 바뀌는 일은 없으므로, 누군가 의도적으로 기록을 막고 있다고 판단했습니다.

3. 분석 과정

메모리 덤프 수집

로그가 계속 사라지는 상황이라 디스크·로그 기반 분석만으로는 한계가 있었습니다. 실행 중인 명령과 레지스트리 데이터가 남아 있는 메모리를 수집하기로 했습니다.

키워드 필터링

덤프를 Linux로 옮겨 문자열을 추출한 뒤, 침해 행위와 관련된 키워드로 범위를 좁혔습니다.

strings -el memory.dmp > dump_utf16.txt     # Windows 문자열(UTF-16LE)
strings     memory.dmp > dump_ascii.txt
grep -inE 'auditpol|schtasks|winreg|wget|cmd\.exe' dump_*.txt
키워드의심 이유
auditpol감사 정책 조작
schtasks악성 예약 작업 등록
winreg레지스트리 조작
wget외부 통신·추가 다운로드
cmd.exe명령 실행

4. 분석 결과

감사 정책 초기화 명령

auditpol.exe /clear /y

시스템 감사 정책을 모두 '감사 안 함'으로 초기화하는 명령입니다. 이후 보안 이벤트가 기록되지 않아 로그 공백이 생겼고, 이를 주기적으로 반복해 침입 흔적을 숨기고 있었습니다.

확장자를 위장한 악성 파일

파일명401-1.htm (IIS 기본 에러 페이지 이름 사칭)
실제 형식Microsoft Cabinet(CAB) 압축 파일, 내부 파일 14개 (file 명령으로 확인)
VirusTotal약 60개 엔진 중 1개만 트로이 목마로 탐지
국내 백신미탐지

정상 작업으로 위장한 예약 작업

덤프 안의 레지스트리 데이터(...\Schedule\TaskCache\Tasks\{GUID})에서 악성 예약 작업을 찾았습니다.

작업 이름MemoryDiagnostic (Windows 기본 작업 이름 사칭)
작성자 표기Microsoft Corporation (사칭)
실행 대상401-1.htm
목적주기적 악성 명령 실행 및 감사 정책 초기화

5. 추정 공격 흐름

1) 파일 업로드 기능 악용 → 악성 파일 업로드
        ↓
2) IIS 작업자 프로세스(w3wp.exe) 권한으로 시스템 명령 실행 (ASP WScript.Shell 악용 추정)
        ↓
3) 'MemoryDiagnostic' 이름으로 예약 작업 등록 (지속성 확보)
        ↓
4) 2~3분마다 auditpol /clear 실행 → 감사 기록 차단
        ↓
5) 401-1.htm(CAB)으로 추가 악성 행위 (백도어 가능성)

재발 여부 점검 명령

# 감사 정책 상태 확인
auditpol /get /category:*

# Microsoft 이름을 쓰는 예약 작업 중 실행 대상이 의심스러운 것 확인
Get-ScheduledTask | Where-Object { $_.Actions.Execute -notmatch 'system32|Program Files' } |
  Select-Object TaskPath, TaskName, @{n='Exec';e={$_.Actions.Execute}}

# 감사 정책 변경 이벤트 (Event ID 4719)
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4719} -MaxEvents 20

7. 분석 한계와 개선 권고

한계

  • 여러 고객이 업로드하는 서비스라 최초 업로드 사용자를 특정하지 못했습니다.
  • OS 이미지 백업이 3개월분만 남아 있었고, 가장 오래된 백업에도 이미 악성 파일이 있어 감염 시점을 확인하지 못했습니다.

개선 권고

  • 백업 보존 기간 연장 (3개월 → 1년 이상)
  • 업로드 파일 실시간 악성코드 검사, 허용 확장자 화이트리스트 적용
  • 업로드 폴더 스크립트 실행 권한 제거, 앱풀 최소 권한 정기 점검
  • 감사 정책 변경(Event ID 4719) 실시간 알림
  • EDR 도입 검토, 정기적인 프로세스·메모리 점검

8. 정리

  • 백신 우회: 60개 엔진 중 1개만 탐지하는 악성코드로 기존 보안 솔루션을 피했습니다.
  • 흔적 은폐: 감사 정책을 주기적으로 초기화해 탐지를 피했습니다.
  • 정상 위장: IIS 에러 페이지 이름과 Microsoft 작업 이름으로 위장했습니다.

로그 공백이라는 작은 이상 징후를 그냥 넘기지 않고 메모리까지 추적한 덕분에 찾아낸 사례로, 백신에만 의존하지 않는 능동적 위협 탐지(Threat Hunting)의 필요성을 보여줍니다.
