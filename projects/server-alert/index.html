서버 장애 SMS 알림 (알리고 · textbee · ELK)

bash 점검 스크립트와 ELK 중앙 감시로 장애를 찾아내고, 상태가 바뀔 때만 문자로 알려주는 알림 시스템입니다. 문자 발송은 알리고와 textbee.dev 중에서 고를 수 있습니다.

1. 구성

[각 서버]  server_check.sh (cron 1분)
             디스크 · 메모리 · 부하 · 서비스 · 포트 · URL
                 │
[ELK 서버] elk_check.sh (cron 1분)      ◀── Metricbeat (Linux · Windows 서버)
             수집 중단(서버 다운) · CPU · 메모리 · 디스크
                 │
            lib_common.sh  상태 비교 → 장애 / 지속 / 복구 판단 → 한 통으로 묶음
                 │
        ┌────────┴────────┐
  sms_aligo.sh       sms_textbee.sh        ← alert.conf 의 SMS_PROVIDER 로 선택
  (문자 서비스 업체)   (안드로이드 폰 SIM)
파일역할
alert.conf발송 업체, 수신자, 기준값, Elasticsearch 접속 정보
lib_common.sh상태 관리(중복 방지·재알림·복구), 메시지 묶음 발송, 실행 잠금
sms_aligo.sh / sms_textbee.sh문자 발송 모듈 (같은 send_sms 함수)
server_check.sh기본: 서버 로컬 점검
elk_check.sh심화: ELK 데이터로 전체 서버 중앙 점검

2. 알림 규칙

매분 점검하더라도 같은 장애로 문자가 계속 오면 알림을 무시하게 됩니다. 점검 대상마다 상태 파일(FAIL 시작시각 마지막알림시각)을 두고, 상태가 바뀔 때만 보냅니다.

상황문자
정상 → 장애[장애] web01 디스크 /var 93% (기준 90%)
장애 지속설정한 간격(기본 60분)마다 [지속 1시간 5분] ...
장애 → 정상[복구] web01 디스크 /var 70% (장애 시간 1시간 12분)
변화 없음보내지 않음
 
# lib_common.sh (핵심 부분)
check_result() {          # check_result <키> <OK|FAIL> <대상> <상세>
    local key=$1 status=$2 target=$3 detail=$4
    local f prev_status="OK" start=$NOW last=0
    f=$(_state_file "$key")
    [ -f "$f" ] && read -r prev_status start last < "$f"

    if [ "$status" = "FAIL" ]; then
        if [ "$prev_status" != "FAIL" ]; then                      # 새 장애
            PENDING_MSGS+=("[장애] $target $detail")
            PENDING_STATE+=("$f|FAIL $NOW $NOW")
        elif [ $((NOW - last)) -ge $((REMIND_MIN * 60)) ]; then     # 장애 지속
            PENDING_MSGS+=("[지속 $(_fmt_dur $((NOW - start)))] $target $detail")
            PENDING_STATE+=("$f|FAIL $start $NOW")
        fi
    elif [ "$prev_status" = "FAIL" ]; then                         # 복구
        PENDING_MSGS+=("[복구] $target $detail (장애 시간 $(_fmt_dur $((NOW - start))))")
        PENDING_STATE+=("$f|")
    fi
}
  • 묶음 발송: 한 번 실행에서 생긴 알림은 한 통으로 합쳐 보냅니다.
  • 발송 실패 대비: 문자 발송에 성공했을 때만 상태를 저장하므로, 실패하면 다음 실행에서 다시 보냅니다.
  • 중복 실행 방지: 점검이 1분을 넘겨도 cron이 겹쳐 돌지 않도록 flock으로 잠급니다.

3. 문자 발송: 두 가지 방식

구분알리고textbee.dev
방식문자 서비스 업체 API본인 안드로이드 폰이 SIM으로 직접 발송
사전 준비발신번호 등록, 발송 서버 IP 등록폰에 textbee 앱 설치, API 키 발급
비용건당 과금통신사 요금제 (무료 플랜 있음)
장문90바이트 초과 시 LMS 자동 전환자동 분할 발송
주의미등록 IP는 -101 인증 오류폰이 꺼지거나 오프라인이면 발송 실패

두 모듈 모두 같은 send_sms "메시지" 함수를 제공하므로, 점검 스크립트는 고칠 필요 없이 설정 한 줄로 바꿉니다.

# alert.conf
SMS_PROVIDER="aligo"      # aligo | textbee

알리고 모듈 (핵심 부분)

# EUC-KR 기준 90바이트 초과 시 LMS
if bytes=$(printf '%s' "$msg" | iconv -f UTF-8 -t EUC-KR 2>/dev/null | wc -c) && [ "$bytes" -le 90 ]; then
    msg_type="SMS"
else
    msg_type="LMS"
fi

for attempt in 1 2; do
    # 알리고는 등록된 IPv4로만 허용 → -4
    resp=$(curl -4 -sS --max-time 15 https://apis.aligo.in/send/ \
        --data-urlencode "user_id=$ALIGO_USER_ID" --data-urlencode "key=$ALIGO_API_KEY" \
        --data-urlencode "sender=$ALIGO_SENDER"   --data-urlencode "receiver=$receivers" \
        --data-urlencode "msg=$msg"               --data-urlencode "msg_type=$msg_type")
    code=$(jq -r '.result_code | tostring' <<<"$resp")
    [ "$code" = "1" ] && return 0
    # IP 인증 오류(-101)일 때만 한 번 더 시도
    [ "$code" = "-101" ] && grep -q 'IP' <<<"$resp" || break
    sleep 1
done
return 1

textbee 모듈 (핵심 부분)

# 010... → +8210... (SIM 발송은 국제 형식이 가장 안전)
for n in "${RECIPIENTS[@]}"; do
    n=${n//[^0-9+]/}

    -X POST "$TEXTBEE_BASE_URL/gateway/send-sms" \

# 200 = 대기열 접수 / 400 = 기기 오프라인 / 401 = 키 오류 / 429 = 요금제 한도
[ "$http" = "200" ] && [ "$(jq -r '.data.success' "$resp_file")" = "true" ]

4. 기본: 서버 로컬 점검 (server_check.sh)

항목방법기본 기준
디스크df -P 마운트별 사용률90% 이상
메모리/proc/meminfo의 MemAvailable 비율10% 이하
부하5분 load ÷ CPU 코어 수코어당 2.0 이상
서비스systemctl is-activeactive 아님
포트bash /dev/tcp 연결3초 내 응답 없음
URLcurl 응답 코드2xx·3xx 아님
 
# 디스크 (마운트별)
while read -r use mount; do
    use=${use%\%}
    if [ "$use" -ge "$DISK_PCT" ]; then
        check_result "disk:$mount" FAIL "$HOST" "디스크 $mount ${use}% (기준 ${DISK_PCT}%)"
    else
        check_result "disk:$mount" OK   "$HOST" "디스크 $mount ${use}%"
    fi
done < <(df -P -x tmpfs -x devtmpfs -x overlay | awk 'NR>1 {print $5, $6}')

# TCP 포트
for hp in "${PORTS[@]}"; do
    h=${hp%:*}; p=${hp##*:}
    if timeout 3 bash -c "exec 3<>/dev/tcp/$h/$p" 2>/dev/null; then
        check_result "port:$hp" OK   "$HOST" "포트 $hp 응답"
    else
        check_result "port:$hp" FAIL "$HOST" "포트 $hp 응답 없음"
    fi
done

flush_alerts

5. 심화: ELK 중앙 점검 (elk_check.sh)

왜 필요한가

서버가 완전히 죽거나 네트워크가 끊기면 그 서버의 server_check.sh는 문자를 보낼 수 없습니다. 이미 구축한 ELK에는 모든 서버의 Metricbeat 데이터가 모이므로, 데이터가 끊긴 서버를 찾으면 서버 다운까지 감지할 수 있습니다.

→ Elasticsearch 모니터링 구축 프로젝트

왜 Kibana 알림이 아니라 스크립트인가

Kibana 무료(Basic) 라이선스는 알림 커넥터가 Index와 Server log 두 가지뿐이라 외부로 문자를 보낼 수 없습니다(Webhook은 유료). 그래서 스크립트가 Elasticsearch를 직접 조회해 판단하고, 발송은 위의 모듈을 그대로 씁니다.

점검 항목

항목Metricbeat 필드판단
수집 중단host.name별 최신 @timestamp5분 이상 데이터 없음 → 서버 다운·네트워크 단절 의심
CPUsystem.cpu.total.norm.pct최근 5분 평균 90% 이상
메모리system.memory.actual.used.pct최근 5분 평균 90% 이상
디스크system.filesystem.used.pct마운트별 최근 10분 최대 90% 이상

수집 중단 감지 쿼리

HOSTS_JSON=$(es_search '{
  "size": 0,
  "query": { "range": { "@timestamp": { "gte": "now-24h" } } },
  "aggs": { "hosts": {
      "terms": { "field": "host.name", "size": 1000 },
      "aggs": { "last_seen": { "max": { "field": "@timestamp" } } }
  } }
}')

# Elasticsearch 조회 자체가 실패하면 그것도 장애로 알림 (감시 시스템 자체 감시)
if [ $? -ne 0 ]; then
    check_result "elk:query" FAIL "ELK" "Elasticsearch 조회 실패"
    flush_alerts; exit 1
fi

while read -r host last_ms; do
    age_min=$(( (NOW - last_ms / 1000) / 60 ))
    if [ "$age_min" -ge "$ELK_NODATA_MIN" ]; then
        check_result "elk:nodata:$host" FAIL "$host" "수집 중단 ${age_min}분 (서버 다운 또는 네트워크 단절 의심)"
    else
        check_result "elk:nodata:$host" OK   "$host" "수집 재개"
    fi
done < <(jq -r '.aggregations.hosts.buckets[] | "\(.key) \(.last_seen.value | floor)"' <<<"$HOSTS_JSON")

최근 24시간 안에 데이터를 보낸 적이 있는 호스트를 감시 대상으로 보므로, 서버를 새로 추가해도 설정을 바꿀 필요가 없습니다. Linux와 Windows 서버 모두 같은 방식으로 점검합니다.

DRY_RUN=1로 실행하면 실제로 보내지 않고 화면에만 출력해, 기준값과 문구를 미리 확인할 수 있습니다.

DRY_RUN=1 /opt/server-alert/server_check.sh

# cron 등록

* * * * * /opt/server-alert/elk_check.sh        # ELK 서버

7. 검증

각 API 응답을 모의로 만들어 다음 상황을 시험했습니다.

  • 장애 발생 → 변화 없음(미발송) → 60분 경과 재알림 → 복구 순서
  • 알리고 IP 인증 오류(-101) 후 재시도 성공
  • textbee 번호 국제 형식 변환, 기기 오프라인(400) 시 상태 미저장 후 재시도
  • ELK 수집 중단·복구 감지, 제외 호스트 처리, Elasticsearch 접속 실패 알림

8. 운영 시 주의사항

  • ELK 서버 자신: ELK 서버가 죽으면 중앙 점검도 멈추므로, ELK 서버에서도 server_check.sh로 elasticsearch·kibana 서비스와 9200 포트를 점검합니다.
  • 비밀값: API 키가 든 alert.conf와 ES 비밀번호 파일은 600 권한으로 두고, 웹 루트 밖에 둡니다. Elasticsearch는 metricbeat-* 읽기 전용 계정으로 조회합니다.
  • textbee 기기 관리: 알림용 폰은 충전과 네트워크 연결을 유지해야 하며, 장애 시 폰 상태도 함께 확인합니다.
  • 점검 대상 제거: 장애 중이던 대상을 설정에서 빼면 상태 파일이 남으므로 함께 지웁니다.
